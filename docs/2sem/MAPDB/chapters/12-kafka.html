12  Apache Kafka

12.1 Introduction to Message Streaming

Modern applications increasingly rely on the ability to ingest, route, and process continuous data streams in real time — sensor networks, financial transactions, application event logs, IoT devices, and more. A dedicated message broker is often placed at the centre of such architectures.

Apache Kafka is a distributed event streaming platform originally developed at LinkedIn (2011) and later open-sourced through the Apache Software Foundation. It provides:

  • High-throughput, low-latency publish/subscribe messaging.
  • Durable, fault-tolerant storage of streams as ordered logs.
  • Scalable partitioned architecture that distributes load across many brokers.

12.1.1 Core Concepts

Concept Description
Topic A named channel to which producers publish and from which consumers read. Topics are partitioned across broker nodes.
Partition An ordered, immutable log of records within a topic. New messages are always appended.
Offset The position of a message within a partition. Consumers track their reading offset.
Producer An application that publishes messages to Kafka topics.
Consumer An application that subscribes to topics and reads messages.
Consumer Group A set of consumers that cooperate to read from a topic; each partition is assigned to exactly one consumer in the group.
Broker A Kafka server that stores and serves partitions. A cluster has multiple brokers for fault tolerance.

12.2 Kafka Architecture

12.2.1 Brokers and Clusters

A Kafka cluster consists of multiple brokers — server processes that store and serve partitions. Topics are spread across brokers; each partition lives on exactly one broker at a time (its leader), with additional follower copies on other brokers for fault tolerance.

Topic "events" — 3 partitions, replication factor 2:

  Broker 1         Broker 2         Broker 3
  ──────────────   ──────────────   ──────────────
  Partition 0 (L)  Partition 0 (F)
                   Partition 1 (L)  Partition 1 (F)
  Partition 2 (F)                   Partition 2 (L)

  L = Leader  (handles all reads and writes for that partition)
  F = Follower (replicates the leader; takes over if leader fails)

The replication factor (number of copies of each partition) is set per topic. A replication factor of 3 tolerates 2 broker failures without data loss.

12.2.2 Consumer Offset Management

Each consumer tracks its position in a partition using an offset — the sequence number of the last message processed. Offsets are committed back to Kafka so that a consumer can resume after a restart.

The auto_offset_reset parameter controls where a consumer starts when no committed offset exists:

Value Behaviour
'earliest' Start from the very beginning of the partition log
'latest' Start from the next new message (default)
'none' Raise an error if no committed offset is found

12.3 Delivery Semantics

Kafka provides three delivery guarantees, depending on how producers and consumers are configured:

Semantic Description Configuration
At-most-once Messages may be lost; never duplicated Producer: acks=0; Consumer: auto-commit before processing
At-least-once Messages are never lost; may be delivered more than once Producer: acks=all + retries; Consumer: commit after processing
Exactly-once Messages processed exactly once — no loss, no duplication Transactional producer + idempotent consumer; requires Kafka ≥ 0.11

Most applications use at-least-once semantics and make their processing logic idempotent (safe to re-execute with the same message). True exactly-once requires transactional APIs and is more complex to implement.

Delivery semantics are a key concern when Kafka feeds a Spark Structured Streaming pipeline (as shown in the KafkaSpark_StructuredStreaming notebook). Spark’s checkpointing mechanism can achieve end-to-end exactly-once semantics when combined with an idempotent sink and Kafka’s transactional API.

12.3.1 Pub/Sub Decoupling

A key architectural feature of Kafka is the complete decoupling of producers and consumers. A producer does not need to know which consumers exist; a consumer does not need to know which producers are publishing. Messages are written to the topic log and remain available for consumption according to retention policy (time- or size-based), not according to whether a consumer has read them.

This enables flexible, scalable architectures: new consumers can read from the beginning of a topic log without affecting producers or other consumers.

12.3.2 Partitions and Keys

When a producer sends a message without a key, Kafka distributes messages across partitions using a round-robin (or load-based) strategy. When a message includes a key, Kafka uses a hash of the key to consistently route all messages with the same key to the same partition — guaranteeing ordering within that group.

Partitioning provides both scalability (different partitions can be processed by different consumers in parallel) and ordering guarantees (within a partition).

12.4 Kafka and Spark Structured Streaming

Kafka can act as both the Source and the Sink for a Spark Structured Streaming pipeline. This connects the Source/Sink abstraction introduced in Apache Spark with Kafka’s pub/sub model:

  • Source: Spark reads a stream of JSON messages from a Kafka topic using .readStream.format("kafka")
  • Transform: Spark parses, filters, and aggregates the stream using DataFrame operations
  • Sink: results are written back to a Kafka topic or to the console using .writeStream

Achieving end-to-end exactly-once semantics requires: (1) Kafka’s transactional producer, (2) Spark checkpointing, and (3) an idempotent sink.
