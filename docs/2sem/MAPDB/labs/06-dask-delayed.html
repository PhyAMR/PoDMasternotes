19.1 The idea behind it

  • Task graphs are the common language of parallel computing. Spark’s DAG, Dask’s graph and a Makefile are the same idea: nodes are pieces of work, edges are dependencies, and anything without a path between them can run in parallel. The scheduler’s job is to find that parallelism and place tasks on workers.
  • Granularity. Every task has a fixed cost (scheduling, serialisation, network: ~100 µs–1 ms in Dask). Parallelism helps only when each task’s work is much larger than that. Most of this lab’s exercises are deliberately too fine-grained, so you can see the overhead win.
  • Lazy vs eager are two styles of the same machinery: build the whole plan and let the scheduler optimise it (delayed), or start work immediately and keep results remote (futures), the way a batch system or a job queue behaves.

19.3 Dask in one paragraph

Dask is a task scheduler written in Python. You describe work as a graph of Python function calls, and the scheduler sends the calls to workers, respecting dependencies. On top of that it offers collections (bags, arrays, DataFrames) that generate those graphs for you. The ideas are the ones from Spark: partition the data, plan before executing, run close to the data. The difference is that everything, including the scheduler, is Python.

from dask.distributed import Client
client = Client('dask-scheduler:8786')     # service name + scheduler port
client                                     # shows workers, cores, memory, dashboard link

19.4 Lazy: delayed

Three toy functions that each sleep(1) stand in for “real work”:

x = increment(1); y = decrement(2); z = add(x, y)       # plain Python: ~3 s

Wrapping calls in delayed records them instead of running them:

from dask import delayed
x = delayed(increment)(1)
y = delayed(decrement)(2)
z = delayed(add)(x, y)       # instant: z is a *plan*, not a number
z.visualize()                # draws the graph (needs graphviz)
z.compute()                  # runs it: ~2 s

Why 2 s and not 3: the graph shows increment and decrement are independent, so they run in parallel, and add waits for both. Dask found the parallelism from the dependencies; you did not write any threading code.

  • delayed(f)(args) = “call f later”. You can also decorate a function with @dask.delayed.
  • .visualize(optimize_graph=True) shows the graph after Dask’s optimisations; for graphs this simple there is nothing to optimise.
  • .compute() is blocking: it returns when the result is back in the notebook.

19.5 Eager: submit, map and futures

future = client.submit(increment, 1)    # starts running NOW on the cluster
future                                  # status: pending → finished
client.gather(future)                   # bring the result to the notebook

A future is a handle to a result that is being computed, or already exists, on a worker. Data stays there until you gather it. You can pass futures as arguments to further submits, and Dask wires up the dependency without moving data through the notebook:

x = client.submit(increment, 1)
y = client.submit(decrement, 2)
total = client.submit(add, x, y)        # depends on x and y, which may not be ready yet
client.gather(total)

client.map(f, list) submits f once per element, which is the natural way to run the same function over many inputs (a parameter scan, say).

delayed + compute submit/map + gather
when it runs when you call compute() immediately
style build a whole graph, then run it fire tasks as you go
result returned by compute() stays on workers until gather()
analogy Spark transformations + action a batch system

wait(futures) blocks until futures are finished without moving results to the notebook; gather waits and transfers.

19.6 Exercises

1. Parallel for loop. For each element of [1..8]: add a random number, multiply by 10; then sum everything. Do it with delayed, with submit, and with map.

Solution. 

results = [delayed(mult_ten)(delayed(add_rand)(x)) for x in data]
total = delayed(sum)(results)
total.compute()

# eager, element by element
total = client.submit(sum, [client.submit(mult_ten, client.submit(add_rand, x)) for x in data])
# eager, with map
total = client.submit(sum, client.map(mult_ten, client.map(add_rand, data)))
client.gather(total)

The graph is 8 independent chains joined by one sum: a pure “map then reduce”.

2. Tree reduction. Sum a list pairwise (add sleeps 1 s) instead of left to right.

Solution. Keep the plain-Python pairwise loop and wrap only the call: pair_sum = delayed(add)(L[i], L[i+1]). The loop now only builds a binary tree of additions; L[0].compute() runs each level in parallel. 9 elements take \(\lceil\log_2 9\rceil = 4\) levels, so about 4 s, against ~11 s for the sequential loop (it makes 5 + 3 + 2 + 1 calls, padding odd levels with add(x, 0)). This is exactly how distributed reduce works.

3. Word count over ~8000 newsgroup documents.

Solution. 

total = delayed(sum)([delayed(count_words)(doc) for doc in dataset])   # lazy
total = client.submit(sum, client.map(count_words, dataset))           # eager

Compare the timings with the plain loop: the parallel versions are not faster. Counting words in one document takes microseconds, while scheduling a task takes hundreds of microseconds. Too many tiny tasks are the problem, and Dask bags (next lab) fix it by batching elements into partitions.

4. Fibonacci with delayed.

Solution. Each new element depends on the two previous ones, so the graph is a chain: result.visualize(rankdir="LR") shows no branch that could run in parallel. A delayed object can be indexed (fibonacci[i]) and that indexing becomes a task too. Dask gives no speed-up for inherently sequential algorithms.

5–6. Monte Carlo integral and π. One delayed (or submit) call per random point.

Solution. These run slower than plain Python, which is the point of the exercise. 1,000–10,000 tasks of a few microseconds each are dominated by scheduling overhead (each task costs ~100s of µs). The fix is coarser tasks: each task generates a chunk of points and returns a partial count.

With futures, random functions need pure=False:

futures = [client.submit(in_circle, pure=False) for _ in range(num_points)]

By default Dask assumes functions are pure (same inputs give the same output) and deduplicates identical calls by hashing them, so without pure=False all 10,000 calls collapse into one task and you get the same point 10,000 times.

19.7 On a real cluster

  • The scheduler/worker split is the same; only the deployment changes: dask-kubernetes / Dask Gateway on a Kubernetes cluster, dask-jobqueue on a Slurm/PBS HPC cluster (each worker is a batch job), or a managed service such as Coiled.
  • Adaptive scaling (cluster.adapt(minimum=2, maximum=50)) adds workers when tasks queue up and releases them when idle, which matters when you pay per VM-hour.
  • The dashboard you used on :8787 is the main debugging tool in production too: idle workers mean too little parallelism, many tiny tasks mean too fine granularity, and red transfer bars mean too much data movement.
  • Futures are a good fit for parameter scans and simulations on HPC (thousands of independent runs), which is a very common scientific use of Dask.

19.8 Wrap up

client.close(), then docker compose down.

TipTakeaways

  • Futures run immediately and keep results on the workers until gather.
  • Task overhead is ~100 µs: parallelise work that is much bigger than that, in chunks.
  • Sequential algorithms (Fibonacci) stay sequential.
  • Mark random functions pure=False when submitting them.

## Eager: `submit`, `map` and futures

```python
future = client.submit(increment, 1)    # starts running NOW on the cluster
future                                  # status: pending → finished
client.gather(future)                   # bring the result to the notebook
```

A **future** is a handle to a result that is being computed, or already exists, **on a worker**.
Data stays there until you `gather` it. You can pass futures as arguments to further `submit`s, and Dask wires up the dependency without moving data through the notebook:

```python
x = client.submit(increment, 1)
y = client.submit(decrement, 2)
total = client.submit(add, x, y)        # depends on x and y, which may not be ready yet
client.gather(total)
```

`client.map(f, list)` submits `f` once per element, which is the natural way to run the same function over many inputs (a parameter scan, say).

| | `delayed` + `compute` | `submit`/`map` + `gather` |
|---|---|---|
| when it runs | when you call `compute()` | immediately |
| style | build a whole graph, then run it | fire tasks as you go |
| result | returned by `compute()` | stays on workers until `gather()` |
| analogy | Spark transformations + action | a batch system |

`wait(futures)` blocks until futures are finished **without** moving results to the notebook; `gather` waits *and* transfers.
