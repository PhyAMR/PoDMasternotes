22.1 The idea behind it

  • Decoupling with a log. Producers and consumers never know about each other; the broker stores an ordered, durable log in between. New consumers can be added later and replay history, and a slow consumer does not slow down producers. This is the backbone of event-driven architectures.
  • Partitions are the unit of parallelism and ordering, as in Spark: more partitions allow more consumers in parallel, and order is guaranteed only inside one partition. The key decides the partition, so you choose the key for the ordering you need (e.g. per user).
  • Replication for fault tolerance. Each partition has a leader and followers on other brokers (theory). This lab uses one broker, so replication_factor=1, i.e. no fault tolerance at all.
  • Delivery semantics. At-most-once, at-least-once or exactly-once depend on when offsets are committed relative to processing, and on whether writes are idempotent.

22.2 Before you start

cd code/kafka

The broker is reachable inside the Docker network as kafka-broker:9092; it is not published to your laptop, so everything (shell tools, Python clients, Spark) runs in a container.

Notebook 1 installs the client library with !pip install kafka-python. It lives in the container, so you need to repeat it after every docker compose down.

22.3 Kafka in one picture

Kafka is a log, not a queue. A topic is split into partitions; each partition is an append-only, ordered list of records, and each record gets a position, the offset. Producers append to the end. Consumers read from wherever they like and remember their offset. Reading does not delete anything, so many independent consumers can read the same data, at different speeds, now or later. Producers and consumers never talk to each other, only to the broker. That decoupling is the whole point.

22.4 Part 1: from the shell (on the broker)

docker compose exec kafka-broker bash
cd $KAFKA_HOME/bin
./kafka-topics.sh --list     --bootstrap-server kafka-broker:9092
./kafka-topics.sh --create   --topic my_awesome_topic --bootstrap-server kafka-broker:9092
./kafka-topics.sh --describe --topic my_awesome_topic --bootstrap-server kafka-broker:9092

Then open two shells on the broker, one for each side:

./kafka-console-producer.sh --topic my_awesome_topic --bootstrap-server kafka-broker:9092
./kafka-console-consumer.sh --topic my_awesome_topic --bootstrap-server kafka-broker:9092 --from-beginning

Type in the producer and lines appear in the consumer. Start the consumer without --from-beginning and it only shows new messages; with it, it replays everything. The data was kept even though nobody was reading.

--bootstrap-server is just an entry point: the client asks that broker for the cluster layout, then talks to whichever broker leads each partition.

22.5 Part 2: producing from Python (Producer.ipynb)

from kafka import KafkaProducer
producer = KafkaProducer(bootstrap_servers=['kafka-broker:9092'])

producer.send('my_awesome_topic', b'message 1')    # returns a future: queued, NOT sent yet
producer.flush()                                   # force the queue out now

send is asynchronous: messages are buffered and sent in batches, which is how Kafka reaches high throughput. If a script exits right after send without flush() (or close()), the messages may never leave. Values (and keys) are bytes: you choose the serialisation, e.g. json.dumps(d).encode().

Close the producer and create a new one: the topic and its messages are unaffected, because producers are disposable.

Keys. producer.send(topic, key=b'user42', value=...). The key is hashed to choose the partition, so all messages with the same key go to the same partition, in order. Without a key, the producer spreads messages over partitions.

Admin API. Creating topics from Python, with a chosen number of partitions:

from kafka.admin import KafkaAdminClient, NewTopic
admin = KafkaAdminClient(bootstrap_servers=['kafka-broker:9092'])
admin.create_topics([NewTopic(name='a_partitioned_topic', num_partitions=2, replication_factor=1)])
admin.list_topics()

replication_factor=1 because there is a single broker; on a real cluster you would use 3. The notebook ends by sending 20 fake transactions (the JSON from the Spark streaming lab) to a_partitioned_topic, and creating a results topic for later.

22.6 Part 3: consuming (Consumer.ipynb)

from kafka import KafkaConsumer
consumer = KafkaConsumer(bootstrap_servers=['kafka-broker:9092'],
                         consumer_timeout_ms=10000)   # stop iterating after 10 s without messages
consumer.subscribe(['my_awesome_topic'])
for msg in consumer:                                   # polls the broker
    print(msg.partition, msg.offset, msg.key, msg.value)

Without consumer_timeout_ms the for loop never ends (a consumer waits for new data forever), so interrupt the kernel to stop it.

Each record carries its partition, offset, timestamp, key and value. consumer.seek_to_beginning() moves the offset back to 0 and the topic is read again, the Python version of --from-beginning.

On a_partitioned_topic you see messages from partitions 0 and 1 interleaved: order is guaranteed only within a partition, never across the topic.

Reading one partition only. Instead of subscribe (let Kafka decide), assign picks partitions by hand:

from kafka import TopicPartition
c0 = KafkaConsumer(bootstrap_servers=['kafka-broker:9092'], consumer_timeout_ms=10000)
c0.assign([TopicPartition('a_partitioned_topic', 0)])
c0.seek_to_beginning()

22.7 Part 4: consumer groups (Consumer.ipynb + ConsumerGroup.ipynb)

Consumers that share a group_id split the partitions of a topic between them: each partition is read by exactly one member of the group. This is how Kafka scales reading.

consumer_one = KafkaConsumer(bootstrap_servers=['kafka-broker:9092'],
                             client_id='consumer_one', group_id='my_group',
                             auto_offset_reset='earliest', consumer_timeout_ms=10000)
consumer_one.subscribe(['a_partitioned_topic'])

Create consumer_two with the same group_id in ConsumerGroup.ipynb, then run both read loops at the same time (they are separate kernels, i.e. separate processes):

  • consumer_one.assignment() and consumer_two.assignment() show one partition each: the group rebalanced.
  • Each prints only its partition’s messages.
  • Stop one, and after a rebalance the other takes over both partitions.
  • A consumer in a different group would get all messages again: groups are independent readers.

auto_offset_reset='earliest' applies only when the group has no stored offset yet (start from the beginning instead of only new messages). Afterwards the group’s committed offsets win, so a second run continues where the group stopped.

22.8 Part 5: Kafka as Spark source and sink (KafkaSpark_StructuredStreaming.ipynb)

The fraud detector from Spark 3, with the socket replaced by Kafka on both ends:

Producer.ipynb ──► topic a_partitioned_topic ──► Spark (parse, count flags per user) ──► topic results ──► Consumer.ipynb

The Kafka connector is not part of core Spark; it is downloaded when the session starts:

.config("spark.jars.packages", "org.apache.spark:spark-sql-kafka-0-10_2.13:4.1.1")
.config("spark.sql.shuffle.partitions", 4)

Source. Same readStream, different format:

raw = (spark.readStream.format("kafka")
            .option("kafka.bootstrap.servers", "kafka-broker:9092")
            .option("subscribe", "a_partitioned_topic")
            .option("startingOffsets", "latest")      # only messages arriving from now on
            .load())
raw.printSchema()    # key, value (binary), topic, partition, offset, timestamp, ...

Kafka rows are binary key/value plus metadata, so the value is cast to string before parsing the JSON:

parsed = raw.select(from_json(col("value").cast("string"), schema).alias("data")).select("data.*")

Because of startingOffsets = latest, re-run the sending cell in Producer.ipynb after starting the query, or you will see nothing. The console output appears in the Jupyter container log, as in Spark 3.

Transform. Identical to Spark 3, except that the output must look like a Kafka record: a key and a value column, both strings or bytes:

sus = (parsed.where(col('flag') == 1)
             .withColumn('id', concat(col('name'), col('surname')))
             .groupBy('id').count().where(col('count') > 1)
             .withColumn('fraud', lit(1))
             .select(col('id').alias('key'), col('fraud').cast(StringType()).alias('value')))

Sink.

query = (sus.writeStream.outputMode("update").format("kafka")
            .option("kafka.bootstrap.servers", "kafka-broker:9092")
            .option("topic", "results")
            .option("checkpointLocation", "checkpoint")   # required for the Kafka sink
            .start())

The checkpoint directory is where Spark records which input offsets it has processed and its aggregation state, so a restarted query continues instead of starting over. It is created in the notebooks folder; delete it to start from scratch.

Finally, the last section of Consumer.ipynb subscribes to results and prints an “alert” for each flagged user: a third, independent application reacting to Spark’s output. For end-to-end exactly-once behaviour you would also need idempotent or transactional writes on the sink side (see the theory); this lab’s pipeline is at-least-once.

22.9 On a real cluster

  • At least 3 brokers, topics with replication_factor=3, and producers with acks="all" (a write is confirmed only once in-sync replicas have it), together with min.insync.replicas=2. This configuration survives losing a broker without losing data.
  • Security: the commented-out producer/consumer examples in the notebooks (security_protocol="SSL", ssl_cafile=...) are what a real cluster looks like: TLS plus client certificates or SASL credentials.
  • Retention: logs are deleted after a time or size limit (retention.ms), or compacted to keep the last value per key. Kafka is a buffer and a history, not a permanent archive.
  • Consumer lag (latest offset − committed offset per partition) is the key health metric: if it grows, consumers can’t keep up, so add consumers (up to the number of partitions) or partitions.
  • Managed Kafka (AWS MSK, Confluent Cloud) handles brokers and upgrades; the client code is the same as in the notebooks, with different bootstrap_servers and credentials.

22.10 Wrap up

query.stop(), spark.stop(), then docker compose down.

TipTakeaways
  • A topic is a set of append-only, partitioned logs; reading does not consume, and consumers track offsets.
  • send is asynchronous: flush() before exiting.
  • Same key → same partition → ordered; no global order across partitions.
  • Within a group, partitions are shared out (scaling); across groups, everyone gets everything (fan-out).
  • Spark reads Kafka with readStream.format("kafka") and writes back with key/value columns and a checkpoint.
