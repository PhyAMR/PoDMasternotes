14.1 The idea behind it

A relational DBMS is the classic client–server system: one process owns the data on its disk and serialises access to it, and any number of clients send it requests over the network. Two promises make it valuable, both covered in the theory:

  • Structure: a schema with types, keys and constraints, so the server itself rejects inconsistent data.
  • Transactions (ACID): a group of changes is applied entirely or not at all, and concurrent clients don’t see half-done work. commit() in this lab is the visible edge of that machinery: until you commit, your changes are a pending transaction.

The price is that a single server is hard to scale out. It scales up (bigger machine), and beyond that you need read replicas or sharding, which give up some of the guarantees. That trade-off is why the later labs (Spark, Dask, Kafka) exist, and why NoSQL databases relax consistency (CAP / BASE).

14.3 01 — Three ways to talk to the server

The point of this section is that the database is a server process on another machine (the db container), and every tool is just a client sending it SQL over the network.

1. Interactive shell, on the server itself.

docker compose exec db bash          # "ssh" into the server node
mysql -u root -p                     # password: root_pwd
SHOW DATABASES;                      -- every statement ends with ;

2. mysql.connector, a Python driver. You open a connection, then a cursor; the cursor sends statements and holds their results.

import mysql.connector
db  = mysql.connector.connect(user="root", password="root_pwd", host="db")
dbc = db.cursor()

dbc.execute("SHOW DATABASES")
dbc.fetchall()          # or fetchone() / fetchmany(n), or iterate: for row in dbc

Note host="db": the service name from the compose file, not localhost (see addresses).

Two cursor rules explain most errors in this lab:

  • A cursor holds the result of one statement. Fetch everything (or call dbc.reset()) before executing the next one, otherwise you get Unread result found.
  • Statements that change the database (CREATE, INSERT, UPDATE, DELETE, ALTER, DROP) only take effect after db.commit(). Read-only statements (SELECT, SHOW, DESCRIBE, USE) don’t need it.

Connecting as my_user and running the same SHOW DATABASES returns a much shorter list: permissions are enforced by the server, per user.

3. Notebook magic (ipython-sql). The most convenient for exploration:

%load_ext sql
%env DATABASE_URL=mysql+mysqlconnector://root:root_pwd@db
%config SqlMagic.style = '_DEPRECATED_DEFAULT'

Now a cell starting with %%sql is plain SQL, and a line res = %sql SELECT ... puts the result in a Python variable. That result object converts to whatever you need: res.DataFrame(), res.dict(), res.csv(), and it can plot itself (res.bar(), res.plot()).

Use magic for exploring, and the connector when SQL has to sit inside Python logic (loops, parameters, functions).

14.5 03 — Keys, constraints and ALTER TABLE

This is the core of the schema-design part. The goal is a tiny shop database with products, suppliers, and the relationship between them.

Products. An auto-numbered primary key and sensible constraints:

CREATE TABLE IF NOT EXISTS products (
  productID    INT          NOT NULL UNIQUE AUTO_INCREMENT PRIMARY KEY,
  productName  VARCHAR(30)  DEFAULT '',
  unitPrice    FLOAT        NOT NULL DEFAULT 99999.99,
  unitsInStock INT UNSIGNED NOT NULL DEFAULT 0
);

The schema is then evolved step by step, which is how real schemas change over time:

Change Statement
add a column ALTER TABLE products ADD COLUMN isDiscontinued BOOL NOT NULL;
give it a default ALTER TABLE products ALTER isDiscontinued SET DEFAULT 0;
tighten a column ALTER TABLE products MODIFY productName VARCHAR(30) NOT NULL;

MODIFY must restate the full type, because it redefines the column. ALTER ... SET DEFAULT only touches the default.

Suppliers. Same idea, with countryCode CHAR(3) later defaulting to "ITA".

The relationship. A supplier sells many products and a product has many suppliers: a many-to-many relation, which needs a junction table:

CREATE TABLE supplier_to_product (prodID INT NOT NULL, supID INT NOT NULL);

ALTER TABLE supplier_to_product ADD PRIMARY KEY (prodID, supID);     -- composite key
ALTER TABLE supplier_to_product ADD CONSTRAINT FK_prod
      FOREIGN KEY (prodID) REFERENCES products(productID);
ALTER TABLE supplier_to_product ADD CONSTRAINT FK_sup
      FOREIGN KEY (supID)  REFERENCES suppliers(supplierID);

Neither column alone is unique (a product appears once per supplier), but the pair is, so the pair is the key. The foreign keys make the database refuse rows that point to non-existent products or suppliers.

DROP TABLE deletes the table and its rows, and breaks every foreign key pointing at it. The notebook uses it to clean up; on a real database, think twice.

14.6 04 — Inserting, updating, deleting

INSERT INTO products (productName, unitPrice, unitsInStock)
VALUES ('Founders Porter', 4.9, 12);

Name the columns explicitly (“explicit is better than implicit”): it keeps working if the table gains columns, and lets defaults (productID, isDiscontinued) fill themselves in. SELECT * FROM products afterwards shows the auto-increment and the defaults at work.

From Python, use placeholders instead of building the string yourself. It handles quoting and protects against SQL injection. executemany inserts a list in one go:

sql = "INSERT INTO products (productName, unitPrice, unitsInStock) VALUES (%s, %s, %s)"
dbc.executemany(sql, [('Punk IPA', 5.2, 45), ('HB Dunkel', 4.5, 250),
                      ('Forst Xmas', 8.0, 2), ('Damm Complot', 3.7, 120)])
db.commit()

UPDATE and DELETE act on every row matching WHERE. A wrong or missing condition is how data gets lost:

UPDATE products SET isDiscontinued = 1 WHERE productName = "Forst Xmas";
DELETE FROM products WHERE productName LIKE "F%s";   -- starts with F, ends with s

Here only Forst Xmas matches (Founders Porter ends in “r”). With a pattern this loose it is easy to hit more rows than intended, so run the same WHERE as a SELECT first to see what you are about to change.

The junction table is filled with id pairs: (2,1) means “product 2 is sold by supplier 1”. After the DELETE, product id 4 is gone for good (auto-increment never reuses ids), so look the ids up with SELECT before inserting.

Export. mysqldump turns a database into a .sql script that recreates it. Write it into /mapd-workspace/dbs, the folder shared with your laptop:

docker compose exec db bash
mysqldump -u root -p my_db > /mapd-workspace/dbs/my_db.sql

14.7 04 — Basic queries

Read a SELECT in its execution order, not its written order (see the theory): FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

SELECT email FROM suppliers WHERE countryCode = "ITA";
SELECT * FROM products WHERE unitPrice < 5 ORDER BY unitsInStock DESC;

Aggregation. GROUP BY always goes with an aggregate function (COUNT, SUM, AVG, …):

res = %sql SELECT COUNT(countryCode) AS count, countryCode FROM suppliers GROUP BY countryCode;
res.bar()

Joins. The notebook runs the same join four ways on suppliers × supplier_to_product. Compare the outputs:

Form Keeps
FROM a, b WHERE a.id = b.id (implicit) matching pairs, same as INNER JOIN
INNER JOIN ... ON only matching pairs
LEFT JOIN every supplier, NULLs where it sells nothing
RIGHT JOIN every junction row, even if its supplier were missing

Chaining two joins goes from supplier → junction → product, which is how you answer questions across a many-to-many relation:

SELECT suppliers.email
FROM supplier_to_product
INNER JOIN suppliers ON supplier_to_product.supID  = suppliers.supplierID
INNER JOIN products  ON supplier_to_product.prodID = products.productID
WHERE products.productName = "Punk IPA";

14.8 05 — Queries on the world database

Loading a ready-made database is a server-side operation:

docker compose exec db bash
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS world"
mysql -u root -p world < /mapd-workspace/dbs/world.sql

Always start an unknown database the same way: USE world; SHOW TABLES; DESCRIBE city; SELECT * FROM city LIMIT 5;. It has three tables, country (keyed by Code), city (CountryCode → country.Code) and countrylanguage (CountryCode, Language, IsOfficial, Percentage).

The ten questions each practise one idea:

# Question Idea
1 largest population ORDER BY ... DESC LIMIT 1
2 cities in Canada COUNT with WHERE; COUNT(Name) vs COUNT(*) vs COUNT(1) timed with %%timeit, which are equivalent here
3 country with most cities GROUP BY CountryCode + ORDER BY the count
4 languages in Southeast Asia join country ↔︎ countrylanguage, DISTINCT; explore first with Region LIKE "%Asia"
5 5 most spoken languages GROUP BY Language
6 city population in the Caribbean join + SUM; here LEFT/RIGHT/INNER give the same answer
7 countries with a “Kingston” join filtered on the city name
8 25 least dense countries a computed column with an alias: Population/SurfaceArea AS PopDensity
9 GNP of countries independent 1850–1910 BETWEEN a AND b
10 life expectancy vs GNP, Spanish-speaking join + IsOfficial = 1, then plot from Python

A sample, to see the pattern:

-- 3. the country with the most cities
SELECT CountryCode, COUNT(1) AS nCities
FROM city
GROUP BY CountryCode
ORDER BY nCities DESC
LIMIT 1;

For the plots, put the query result in a variable and let it plot itself, e.g. res = %sql SELECT Name, Population/SurfaceArea AS PopDensity FROM country ORDER BY PopDensity ASC LIMIT 25; then res.bar().

14.9 06 — The IMDb database

A larger, realistic schema, loaded like world (CREATE DATABASE IMDb, then mysql ... IMDb < /mapd-workspace/dbs/IMDb_pruned.sql, a couple of minutes). The tables you need are Names_ (people), Titles, Had_role (person ↔︎ title ↔︎ role), Directors, Title_ratings, Title_genres and Episode_belongs_to.

Strategy for every question: DESCRIBE the tables involved, build the query in small steps with LIMIT, then add the aggregation. The solutions do exactly that, and reading the intermediate queries is more useful than the final one.

Birth years. Querying everything at once hides problems; looking at MIN/MAX first reveals impossible birth years (outliers), which you then cut (WHERE birth_year > 1850) before histogramming. The mean and standard deviation are computed on the server with AVG() and STD(), so only two numbers travel back.

Joins across the schema. For “who played Spider-Man”, the solution first writes it with a subquery (WHERE name_id IN (SELECT ...)) and then as an explicit JOIN. Prefer the join: it is clearer, and the optimiser handles it better.

SELECT Names_.name_, Titles.primary_title, Titles.start_year
FROM Had_role
INNER JOIN Titles ON Had_role.title_id = Titles.title_id
INNER JOIN Names_ ON Had_role.name_id  = Names_.name_id
WHERE Had_role.role_ LIKE "Spider-Man" AND Titles.title_type = "movie"
ORDER BY Titles.start_year;

Views. For the “TV series with more than 1000 episodes” question the solution saves intermediate results as views, named queries you can select from like tables:

CREATE VIEW MoreThan1KEpisodes AS
SELECT parent_tv_show_title_id, COUNT(episode_title_id) AS nEpisodes
FROM Episode_belongs_to
GROUP BY parent_tv_show_title_id
HAVING nEpisodes > 1000;          -- HAVING filters groups, WHERE filters rows

Ratings. Grouping by a computed value, here the decade FLOOR(start_year/10)*10, and the syntax %%sql res << SELECT ... that stores a multi-line query’s result in res. For Game of Thrones, Titles is joined twice with different aliases (T for the episode, P for the parent show), which is a common trick when one table plays two roles.

14.10 On a real system

  • The server would be a dedicated VM or a managed service (RDS, Cloud SQL). You connect exactly as here, with host="<address>" instead of "db", usually over TLS.
  • Credentials are never written in notebooks: read them from environment variables or a secrets manager. The root_pwd in the compose file is only acceptable on a throwaway local container.
  • Applications get their own users with only the privileges they need (GRANT SELECT ON world.* TO 'reader'@'%'), as you saw with my_user.
  • mysqldump is the simplest backup; real deployments add replication and point-in-time recovery (Reliability).
  • Big analytical queries are typically not run on the production database: the data is exported (ETL) to a warehouse or to files that Spark/Dask can process in parallel.
TipTakeaways
  • Server and client are separate machines; every tool is a client sending SQL.
  • Changes need commit(); a cursor holds one result at a time.
  • Design: primary keys identify rows, foreign keys enforce relations, many-to-many needs a junction table.
  • Querying: explore with DESCRIBE and LIMIT, aggregate on the server, bring back only small results.

14.13 SQL Query Exercises

Write a single SQL query to retrieve all wines made with ‘Merlot’ or ‘Pinot Noir’ grapes since 2010, sorted by alcohol percentage in descending order.

Solution. (Assumed schema — not a real one: Wines(name, grape, year, alcohol).)

SELECT *
FROM Wines
WHERE grape IN ('Merlot', 'Pinot Noir')
  AND year >= 2010
ORDER BY alcohol DESC;

Write a single SQL query to retrieve the names of professors whose average student grade across all their courses is greater than 24. Consider only sufficient grades (at least 18).

Solution. (Assumed schema — not a real one: Professors(prof_id, name), Courses(course_id, prof_id), Exams(student_id, course_id, grade).)

SELECT p.name
FROM Professors p
JOIN Courses  c ON c.prof_id   = p.prof_id
JOIN Exams    e ON e.course_id = c.course_id
WHERE e.grade >= 18
GROUP BY p.prof_id, p.name
HAVING AVG(e.grade) > 24;

Write a single SQL query to retrieve the maximum and average employee salary per department, limited to departments located in ‘New York’ and ‘Chicago’. Sort the result by department name.

Solution. (Assumed schema — not a real one: Departments(dept_id, name, location), Employees(emp_id, dept_id, salary).)

SELECT d.name             AS department,
       MAX(e.salary)      AS max_salary,
       AVG(e.salary)      AS avg_salary
FROM Departments d
JOIN Employees   e ON e.dept_id = d.dept_id
WHERE d.location IN ('New York', 'Chicago')
GROUP BY d.dept_id, d.name
ORDER BY d.name;

Write a single SQL query to retrieve earthquakes with magnitudes between 6.5 and 7.7 that occurred after 1940 from the quaketable, sorted by epicentral depth (greater than 0) from highest to lowest.

Solution. (Assumed schema — not a real one: quaketable(id, magnitude, year, depth).)

SELECT *
FROM quaketable
WHERE magnitude BETWEEN 6.5 AND 7.7
  AND year > 1940
  AND depth > 0
ORDER BY depth DESC;

Provide SQL queries demonstrating the following:

  • One query using WHERE, AND, and OR.
  • Two queries each using JOIN, ORDER BY (A–Z by name), GROUP BY, and the LIKE operator.

Solution. (All schemas below are hypothetical, not real.)

-- WHERE / AND / OR
SELECT *
FROM Employees
WHERE department = 'Sales'
  AND (salary > 50000 OR years_experience > 5);
-- JOIN + ORDER BY + GROUP BY + LIKE  (1)
SELECT d.name AS department, COUNT(e.emp_id) AS headcount
FROM Departments d
JOIN Employees   e ON e.dept_id = d.dept_id
WHERE e.title LIKE 'Senior%'
GROUP BY d.name
ORDER BY d.name ASC;
-- JOIN + ORDER BY + GROUP BY + LIKE  (2)
SELECT a.name AS author, COUNT(b.book_id) AS books_written
FROM Authors     a
JOIN BookAuthors ba ON ba.author_id = a.author_id
JOIN Books       b  ON b.book_id    = ba.book_id
WHERE b.title LIKE '%Physics%'
GROUP BY a.name
ORDER BY a.name ASC;

Write a single SQL query to retrieve the average years of experience of employees who are older than 30 years and have a salary greater than $50,000, grouped by department.

Solution. (Assumed schema — not a real one: Employees(emp_id, department, age, salary, years_experience).)

SELECT department,
       AVG(years_experience) AS avg_years_experience
FROM Employees
WHERE age > 30
  AND salary > 50000
GROUP BY department;

Using the world database, write a single SQL query to retrieve the average population of cities in each country that has a population greater than 10 million, grouped by continent.

Solution. (Standard world schema — country(Code, Continent, Population), city(CountryCode, Population).)

SELECT c.Continent,
       AVG(ci.Population) AS avg_city_population
FROM country c
JOIN city    ci ON ci.CountryCode = c.Code
WHERE c.Population > 10000000
GROUP BY c.Continent;

Using the world database, write a single SQL query to retrieve the total number of languages spoken in countries that are located in Asia and have a population greater than 50 million, grouped by region.

Solution. (Standard world schema — country(Code, Continent, Region, Population), countrylanguage(CountryCode, Language).)

SELECT c.Region,
       COUNT(DISTINCT cl.Language) AS total_languages
FROM country         c
JOIN countrylanguage cl ON cl.CountryCode = c.Code
WHERE c.Continent  = 'Asia'
  AND c.Population > 50000000
GROUP BY c.Region;

Using the IMDb database, write a single SQL query to retrieve the average movie rating of movies in the “Action” genre that have a runtime of more than 90 minutes, grouped by year.

Solution. (Assumed IMDb-style schema — not the official one: Movies(movie_id, year, runtime), Genres(movie_id, genre), Ratings(movie_id, rating).)

SELECT m.year,
       AVG(r.rating) AS avg_rating
FROM Movies  m
JOIN Genres  g ON g.movie_id = m.movie_id
JOIN Ratings r ON r.movie_id = m.movie_id
WHERE g.genre   = 'Action'
  AND m.runtime > 90
GROUP BY m.year;

Using the IMDb database, write a single SQL query to retrieve the top 5 persons who have worked in the most movies, ordered by the number of movies they have worked in (descending).

Solution. (Assumed schema — not real: Persons(person_id, name), Crew(person_id, movie_id).)

SELECT p.name,
       COUNT(DISTINCT c.movie_id) AS movie_count
FROM Persons p
JOIN Crew    c ON c.person_id = p.person_id
GROUP BY p.person_id, p.name
ORDER BY movie_count DESC
LIMIT 5;

Using the IMDb database, retrieve the average rating of movies in the “Comedy” genre that were released after 2000 and have more than 100,000 votes, grouped by director. Include only directors who have directed more than 5 such movies.

Solution. (Assumed schema — not real: Movies(movie_id, year, votes), Genres(movie_id, genre), Ratings(movie_id, rating), Crew(person_id, movie_id, role), Persons(person_id, name).)

SELECT p.name                  AS director,
       AVG(r.rating)           AS avg_rating
FROM Persons p
JOIN Crew    c ON c.person_id = p.person_id
              AND c.role       = 'director'
JOIN Movies  m ON m.movie_id  = c.movie_id
JOIN Genres  g ON g.movie_id  = m.movie_id
JOIN Ratings r ON r.movie_id  = m.movie_id
WHERE g.genre = 'Comedy'
  AND m.year  > 2000
  AND m.votes > 100000
GROUP BY p.person_id, p.name
HAVING COUNT(DISTINCT m.movie_id) > 5;

Using the IMDb database, retrieve the total number of movies and the average runtime of movies in each genre, considering only movies released after 2010. Group by genre. Exclude genres with 10 or fewer movies and genres where the average runtime is less than 90 minutes.

Solution. (Assumed schema — not real: Movies(movie_id, year, runtime), Genres(movie_id, genre).)

SELECT g.genre,
       COUNT(DISTINCT m.movie_id) AS total_movies,
       AVG(m.runtime)             AS avg_runtime
FROM Movies m
JOIN Genres g ON g.movie_id = m.movie_id
WHERE m.year > 2010
GROUP BY g.genre
HAVING COUNT(DISTINCT m.movie_id) > 10
   AND AVG(m.runtime) >= 90;

```python
db  = mysql.connector.connect(user="root", password="root_pwd", host="db")
dbc = db.cursor()

dbc.execute("SHOW DATABASES")
dbc.fetchall()          # or fetchone() / fetchmany(n), or iterate: for row in dbc
```

Note `host="db"`: the service name from the compose file, not `localhost` (see [addresses](00-running-labs.qmd)).

Two cursor rules explain most errors in this lab:

- A cursor holds the result of **one** statement. Fetch everything (or call `dbc.reset()`) before executing the next one, otherwise you get *Unread result found*.
- Statements that **change** the database (`CREATE`, `INSERT`, `UPDATE`, `DELETE`, `ALTER`, `DROP`) only take effect after `db.commit()`. Read-only statements (`SELECT`, `SHOW`, `DESCRIBE`, `USE`) don't need it.

Connecting as `my_user` and running the same `SHOW DATABASES` returns a much shorter list: permissions are enforced by the server, per user.

**3. Notebook magic (`ipython-sql`).** The most convenient for exploration:

```python
%load_ext sql
%env DATABASE_URL=mysql+mysqlconnector://root:root_pwd@db
%config SqlMagic.style = '_DEPRECATED_DEFAULT'
```

Now a cell starting with `%%sql` is plain SQL, and a line `res = %sql SELECT ...` puts the result in a Python variable.
That result object converts to whatever you need: `res.DataFrame()`, `res.dict()`, `res.csv()`, and it can plot itself (`res.bar()`, `res.plot()`).

Use magic for exploring, and the connector when SQL has to sit inside Python logic (loops, parameters, functions).

## 03 — Keys, constraints and `ALTER TABLE`

This is the core of the schema-design part.
The goal is a tiny shop database with **products**, **suppliers**, and the relationship between them.

**Products.** An auto-numbered primary key and sensible constraints:

```sql
CREATE TABLE IF NOT EXISTS products (
  productID    INT          NOT NULL UNIQUE AUTO_INCREMENT PRIMARY KEY,
  productName  VARCHAR(30)  DEFAULT '',
  unitPrice    FLOAT        NOT NULL DEFAULT 99999.99,
  unitsInStock INT UNSIGNED NOT NULL DEFAULT 0
);
```

The schema is then evolved step by step, which is how real schemas change over time:

| Change | Statement |
|---|---|
| add a column | `ALTER TABLE products ADD COLUMN isDiscontinued BOOL NOT NULL;` |
| give it a default | `ALTER TABLE products ALTER isDiscontinued SET DEFAULT 0;` |
| tighten a column | `ALTER TABLE products MODIFY productName VARCHAR(30) NOT NULL;` |

`MODIFY` must restate the full type, because it redefines the column. `ALTER ... SET DEFAULT` only touches the default.

**Suppliers.** Same idea, with `countryCode CHAR(3)` later defaulting to `"ITA"`.

**The relationship.** A supplier sells many products and a product has many suppliers: a **many-to-many** relation, which needs a *junction table*:

```sql
CREATE TABLE supplier_to_product (prodID INT NOT NULL, supID INT NOT NULL);

ALTER TABLE supplier_to_product ADD PRIMARY KEY (prodID, supID);     -- composite key
ALTER TABLE supplier_to_product ADD CONSTRAINT FK_prod
      FOREIGN KEY (prodID) REFERENCES products(productID);
ALTER TABLE supplier_to_product ADD CONSTRAINT FK_sup
      FOREIGN KEY (supID)  REFERENCES suppliers(supplierID);
```

Neither column alone is unique (a product appears once per supplier), but the **pair** is, so the pair is the key.
The foreign keys make the database refuse rows that point to non-existent products or suppliers.

::: {.callout-warning}
`DROP TABLE` deletes the table *and* its rows, and breaks every foreign key pointing at it. The notebook uses it to clean up; on a real database, think twice.
:::

## 04 — Inserting, updating, deleting

```sql
INSERT INTO products (productName, unitPrice, unitsInStock)
VALUES ('Founders Porter', 4.9, 12);
```

Name the columns explicitly ("explicit is better than implicit"): it keeps working if the table gains columns, and lets defaults (`productID`, `isDiscontinued`) fill themselves in. `SELECT * FROM products` afterwards shows the auto-increment and the defaults at work.

From Python, use **placeholders** instead of building the string yourself. It handles quoting and protects against SQL injection. `executemany` inserts a list in one go:

```python
sql = "INSERT INTO products (productName, unitPrice, unitsInStock) VALUES (%s, %s, %s)"
dbc.executemany(sql, [('Punk IPA', 5.2, 45), ('HB Dunkel', 4.5, 250),
                      ('Forst Xmas', 8.0, 2), ('Damm Complot', 3.7, 120)])
db.commit()
```

`UPDATE` and `DELETE` act on **every row matching `WHERE`**. A wrong or missing condition is how data gets lost:

```sql
UPDATE products SET isDiscontinued = 1 WHERE productName = "Forst Xmas";
DELETE FROM products WHERE productName LIKE "F%s";   -- starts with F, ends with s
```

Here only *Forst Xmas* matches (*Founders Porter* ends in "r"). With a pattern this loose it is easy to hit more rows than intended, so run the same `WHERE` as a `SELECT` first to see what you are about to change.

The junction table is filled with id pairs: `(2,1)` means "product 2 is sold by supplier 1".
After the `DELETE`, product id 4 is gone for good (auto-increment never reuses ids), so look the ids up with `SELECT` before inserting.

**Export.** `mysqldump` turns a database into a `.sql` script that recreates it. Write it into `/mapd-workspace/dbs`, the folder shared with your laptop:

```bash
docker compose exec db bash
mysqldump -u root -p my_db > /mapd-workspace/dbs/my_db.sql
```

## 04 — Basic queries

Read a `SELECT` in its **execution order**, not its written order (see [the theory](../chapters/06-databases.qmd)):
`FROM`/`JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`.

```sql
SELECT email FROM suppliers WHERE countryCode = "ITA";
SELECT * FROM products WHERE unitPrice < 5 ORDER BY unitsInStock DESC;
```

**Aggregation.** `GROUP BY` always goes with an aggregate function (`COUNT`, `SUM`, `AVG`, …):

```python
res = %sql SELECT COUNT(countryCode) AS count, countryCode FROM suppliers GROUP BY countryCode;
res.bar()
```

**Joins.** The notebook runs the same join four ways on `suppliers` × `supplier_to_product`. Compare the outputs:

| Form | Keeps |
|---|---|
| `FROM a, b WHERE a.id = b.id` (implicit) | matching pairs, same as `INNER JOIN` |
| `INNER JOIN ... ON` | only matching pairs |
| `LEFT JOIN` | every supplier, `NULL`s where it sells nothing |
| `RIGHT JOIN` | every junction row, even if its supplier were missing |

Chaining two joins goes from supplier → junction → product, which is how you answer questions across a many-to-many relation:

```sql
SELECT suppliers.email
FROM supplier_to_product
INNER JOIN suppliers ON supplier_to_product.supID  = suppliers.supplierID
INNER JOIN products  ON supplier_to_product.prodID = products.productID
WHERE products.productName = "Punk IPA";
```

## 05 — Queries on the `world` database

Loading a ready-made database is a server-side operation:

```bash
docker compose exec db bash
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS world"
mysql -u root -p world < /mapd-workspace/dbs/world.sql
```

Always start an unknown database the same way: `USE world; SHOW TABLES; DESCRIBE city; SELECT * FROM city LIMIT 5;`.
It has three tables, `country` (keyed by `Code`), `city` (`CountryCode` → `country.Code`) and `countrylanguage` (`CountryCode`, `Language`, `IsOfficial`, `Percentage`).

The ten questions each practise one idea:

| # | Question | Idea |
|---|---|---|
| 1 | largest population | `ORDER BY ... DESC LIMIT 1` |
| 2 | cities in Canada | `COUNT` with `WHERE`; `COUNT(Name)` vs `COUNT(*)` vs `COUNT(1)` timed with `%%timeit`, which are equivalent here |
| 3 | country with most cities | `GROUP BY CountryCode` + `ORDER BY` the count |
| 4 | languages in Southeast Asia | join `country` ↔ `countrylanguage`, `DISTINCT`; explore first with `Region LIKE "%Asia"` |
| 5 | 5 most spoken languages | `GROUP BY Language` |
| 6 | city population in the Caribbean | join + `SUM`; here LEFT/RIGHT/INNER give the same answer |
| 7 | countries with a "Kingston" | join filtered on the city name |
| 8 | 25 least dense countries | a computed column with an alias: `Population/SurfaceArea AS PopDensity` |
| 9 | GNP of countries independent 1850–1910 | `BETWEEN a AND b` |
| 10 | life expectancy vs GNP, Spanish-speaking | join + `IsOfficial = 1`, then plot from Python |

A sample, to see the pattern:

```sql
-- 3. the country with the most cities
SELECT CountryCode, COUNT(1) AS nCities
FROM city
GROUP BY CountryCode
ORDER BY nCities DESC
LIMIT 1;
```

For the plots, put the query result in a variable and let it plot itself, e.g. `res = %sql SELECT Name, Population/SurfaceArea AS PopDensity FROM country ORDER BY PopDensity ASC LIMIT 25;` then `res.bar()`.

## 06 — The IMDb database

A larger, realistic schema, loaded like `world` (`CREATE DATABASE IMDb`, then `mysql ... IMDb < /mapd-workspace/dbs/IMDb_pruned.sql`, a couple of minutes).
The tables you need are `Names_` (people), `Titles`, `Had_role` (person ↔ title ↔ role), `Directors`, `Title_ratings`, `Title_genres` and `Episode_belongs_to`.

Strategy for every question: **`DESCRIBE` the tables involved, build the query in small steps with `LIMIT`, then add the aggregation.**
The solutions do exactly that, and reading the intermediate queries is more useful than the final one.

**Birth years.** Querying everything at once hides problems; looking at `MIN`/`MAX` first reveals impossible birth years (outliers), which you then cut (`WHERE birth_year > 1850`) before histogramming.
The mean and standard deviation are computed *on the server* with `AVG()` and `STD()`, so only two numbers travel back.

**Joins across the schema.** For "who played Spider-Man", the solution first writes it with a subquery (`WHERE name_id IN (SELECT ...)`) and then as an explicit `JOIN`. Prefer the join: it is clearer, and the optimiser handles it better.

```sql
SELECT Names_.name_, Titles.primary_title, Titles.start_year
FROM Had_role
INNER JOIN Titles ON Had_role.title_id = Titles.title_id
INNER JOIN Names_ ON Had_role.name_id  = Names_.name_id
WHERE Had_role.role_ LIKE "Spider-Man" AND Titles.title_type = "movie"
ORDER BY Titles.start_year;
```

**Views.** For the "TV series with more than 1000 episodes" question the solution saves intermediate results as *views*, named queries you can select from like tables:

```sql
CREATE VIEW MoreThan1KEpisodes AS
SELECT parent_tv_show_title_id, COUNT(episode_title_id) AS nEpisodes
FROM Episode_belongs_to
GROUP BY parent_tv_show_title_id
HAVING nEpisodes > 1000;          -- HAVING filters groups, WHERE filters rows
```

**Ratings.** Grouping by a computed value, here the decade `FLOOR(start_year/10)*10`, and the syntax `%%sql res << SELECT ...` that stores a multi-line query's result in `res`.
For Game of Thrones, `Titles` is joined **twice** with different aliases (`T` for the episode, `P` for the parent show), which is a common trick when one table plays two roles.

## On a real system

- The server would be a dedicated VM or a managed service (RDS, Cloud SQL). You connect exactly as here, with `host="<address>"` instead of `"db"`, usually over TLS.
- **Credentials are never written in notebooks**: read them from environment variables or a secrets manager. The `root_pwd` in the compose file is only acceptable on a throwaway local container.
- Applications get their own users with only the privileges they need (`GRANT SELECT ON world.* TO 'reader'@'%'`), as you saw with `my_user`.
- `mysqldump` is the simplest backup; real deployments add replication and point-in-time recovery ([Reliability](../chapters/03-reliability-security.qmd)).
- Big analytical queries are typically not run on the production database: the data is exported (ETL) to a warehouse or to files that Spark/Dask can process in parallel.

::: {.callout-tip}
## Takeaways
- Server and client are separate machines; every tool is a client sending SQL.
- Changes need `commit()`; a cursor holds one result at a time.
- Design: primary keys identify rows, foreign keys enforce relations, many-to-many needs a junction table.
- Querying: explore with `DESCRIBE` and `LIMIT`, aggregate on the server, bring back only small results.
:::

## SQL String Functions Reference

| Function | Description | Example |
|---|---|---|
| `CONCAT(a, b, ...)` | Concatenate strings | `CONCAT(first_name, ' ', last_name)` |
| `SUBSTRING(str, pos, len)` | Extract a substring | `SUBSTRING(name, 1, 3)` |
| `UPPER(str)` / `LOWER(str)` | Change case | `UPPER('hello')` → `'HELLO'` |
| `TRIM(str)` | Remove leading/trailing spaces | `TRIM('  hello  ')` → `'hello'` |
| `LEFT(str, n)` / `RIGHT(str, n)` | First/last n characters | `LEFT('hello', 3)` → `'hel'` |
| `LENGTH(str)` | String length in bytes | `LENGTH('hello')` → `5` |
| `REPLACE(str, from, to)` | Replace all occurrences | `REPLACE('aababc', 'ab', 'X')` → `'aXXc'` |
| `LOCATE(substr, str)` | Find position of substring | `LOCATE('ll', 'hello')` → `3` |
| `FORMAT(num, d)` | Format number with d decimal places | `FORMAT(1234567.891, 2)` → `'1,234,567.89'` |

```sql
-- Example: build a full name and show first 10 characters
SELECT UPPER(CONCAT(first_name, ' ', last_name)) AS full_name,
       SUBSTRING(bio, 1, 100) AS bio_preview
FROM Authors;
```

## SQL Date and Time Functions Reference

| Function | Description | Example |
|---|---|---|
| `NOW()` / `CURRENT_TIMESTAMP` | Current date and time | `NOW()` → `2024-05-28 14:32:00` |
| `CURRENT_DATE` | Today's date | `CURRENT_DATE` → `2024-05-28` |
| `DATE_ADD(date, INTERVAL n unit)` | Add an interval | `DATE_ADD('2024-01-01', INTERVAL 30 DAY)` |
| `DATE_SUB(date, INTERVAL n unit)` | Subtract an interval | `DATE_SUB(NOW(), INTERVAL 1 YEAR)` |
| `DATEDIFF(d1, d2)` | Days between two dates | `DATEDIFF('2024-12-31', '2024-01-01')` → `365` |
| `TIMESTAMPDIFF(unit, t1, t2)` | Difference in specified unit | `TIMESTAMPDIFF(MONTH, '2023-01-01', '2024-05-01')` → `16` |
| `DATE_FORMAT(date, fmt)` | Format a date | `DATE_FORMAT(NOW(), '%Y-%m-%d')` |
| `EXTRACT(unit FROM date)` | Extract a component | `EXTRACT(YEAR FROM '2024-05-28')` → `2024` |
| `YEAR(d)` / `MONTH(d)` / `DAY(d)` | Extract components | `YEAR(NOW())` → `2024` |

```sql
-- Example: find orders placed in the last 30 days
SELECT order_id, order_date, total
FROM Orders
WHERE order_date >= DATE_SUB(CURRENT_DATE, INTERVAL 30 DAY)
ORDER BY order_date DESC;
```

::: {.exercise}
Write a single SQL query to retrieve the names of professors whose average student grade across all their courses is greater than 24. Consider only sufficient grades (at least 18).
:::

::: {.solution}

*(Assumed schema — not a real one: `Professors(prof_id, name)`, `Courses(course_id, prof_id)`, `Exams(student_id, course_id, grade)`.)*

```sql
SELECT p.name
FROM Professors p
JOIN Courses  c ON c.prof_id   = p.prof_id
JOIN Exams    e ON e.course_id = c.course_id
WHERE e.grade >= 18
GROUP BY p.prof_id, p.name
HAVING AVG(e.grade) > 24;
```

```sql
GROUP BY d.dept_id, d.name
ORDER BY d.name;
```

::: {.exercise}
Using the IMDb database, retrieve the average rating of movies in the "Comedy" genre that were released after 2000 and have more than 100,000 votes, grouped by director. Include only directors who have directed more than 5 such movies.

```sql
SELECT p.name                  AS director,
       AVG(r.rating)           AS avg_rating
FROM Persons p
JOIN Crew    c ON c.person_id = p.person_id
              AND c.role       = 'director'
JOIN Movies  m ON m.movie_id  = c.movie_id
JOIN Genres  g ON g.movie_id  = m.movie_id
JOIN Ratings r ON r.movie_id  = m.movie_id
WHERE g.genre = 'Comedy'
  AND m.year  > 2000
  AND m.votes > 100000
GROUP BY p.person_id, p.name
HAVING COUNT(DISTINCT m.movie_id) > 5;
```

::: {.exercise}
Using the IMDb database, retrieve the total number of movies and the average runtime of movies in each genre, considering only movies released after 2010. Group by genre. Exclude genres with 10 or fewer movies and genres where the average runtime is less than 90 minutes.
:::

::: {.solution}

*(Assumed schema — not real: `Movies(movie_id, year, runtime)`, `Genres(movie_id, genre)`.)*

```sql
SELECT g.genre,
       COUNT(DISTINCT m.movie_id) AS total_movies,
       AVG(m.runtime)             AS avg_runtime
FROM Movies m
JOIN Genres g ON g.movie_id = m.movie_id
WHERE m.year > 2010
GROUP BY g.genre
HAVING COUNT(DISTINCT m.movie_id) > 10
   AND AVG(m.runtime) >= 90;
```
